## Stage 1 of the Local Workspace Runtime roadmap

**Status:** Handoff-ready single-user beta blueprint; implementation has not started; exhaustive hardening is post-beta
**Date:** 2026-08-28
**Scope revision:** 2026-08-29
**Overall strategy:** [Local Workspace Runtime — Overall Strategy and Roadmap](./00-overall-strategy.md)

## 1. Goal

Ship a coherent single-user beta of Astrid on the new local workspace architecture and publish the neutral contracts Stage 2 REIGH consumes. An Astrid launch from the editable checkout must create or open one workspace realm, start or connect to its independently owned runtime, initialize SQLite and the content-addressed object store, provision Astrid's scoped identity, start one generic Astrid pack-executor host, and become broadly useful without Supabase, Turso, REIGH, Reigh Worker, or cloud infrastructure.

This implements the first landmark of the canonical roadmap:

- Banodoco Workspace Runtime remains the sole workspace, database, object, event, and task authority.
- Astrid is the first complete product client of that runtime; it does not own or embed the runtime.
- Every durable structured Astrid fact goes through the runtime into SQLite.
- Every durable imported or generated byte goes through the runtime into the managed object store.
- Stage 2 attaches basic REIGH only after Astrid's authority/capability cutover; fuller REIGH and Reigh Worker work follows from that same client boundary.

The governing rule is:

> **Astrid-first is release sequencing, not ownership sequencing.**

> **Stage 1 is parallel-first and elastically subagented.** T0–T6 are convergence gates, not calendar phases. One root/coordinator agent dispatches the graph. One worker subagent may walk it alone; 100+ worker subagents may claim every ready, non-overlapping packet on its frontier. Scale is optional and used only when it shortens the path to integrated evidence. Scale at the leaves—domains, capability families, fixtures, migration mappings, and proofs—not by creating competing authors of the runtime contract, generated clients, generic-host core, live migration, or release candidate.

## 2. Stage boundary

| Stage 1 owns | Stage 1 publishes | Stage 2 owns |

## 3. Scope of the single-user beta

The beta contains these independently bounded components and source surfaces:

1. `banodoco-workspace-runtime`: independently runnable sibling checkout/service containing the daemon, SQLite schema/migrations, local CAS, protocol, realm lifecycle, doctor, backup, restore, export, and conformance suite.
2. generated `banodoco-workspace-client` Python and `@banodoco/workspace-client` TypeScript clients plus their shared conformance fixtures. Astrid uses Python first; TypeScript is generated and proven before Astrid ships so the contract is not accidentally Python-shaped.
3. Astrid editable checkout: the post-cutover product CLI, public SDK/facades, pack discovery and authoring, skills and `STAGE.md` guidance, agent planning/supervision, and zero-logic product-launch wrapper.
4. one generic Astrid pack-executor host: a separate process that loads CPU, agent/GPT, configured-provider, render, and supported local-generation capabilities from the editable checkout, uses tool/GPU subprocesses only where environment isolation requires them, and advertises only what passes preflight.
5. rendering remains an Astrid pack capability executed by that generic host with the repository's locked Node/Remotion/FFmpeg environment. Its task/input/output/settlement contract is neutral; Stage 1 does not create a separate render implementation repository or lifecycle.
6. neutral `banodoco-local` bootstrap plus Astrid beta source manifest: explicit checkout paths, Git revisions, dirty-tree/source digests, dependency lock digests, discovery, launch, restart, backup, and recovery logic. Astrid invokes this state machine; it does not reimplement it.
7. one repo-local, separately invoked migration program/runbook for this machine only. It is absent from normal runtime/Astrid graphs and is retained with its source backup and validation report, but it is not a supported general migration product.

### 3.1 Beta delivery model: open editable source

Stage 1 is not an installer or binary-packaging project. The supported current-machine composition uses explicit source checkouts, editable Python installs, and repository-pinned Node dependencies. The source checkout is allowed to change because it is the creative engine people will work on directly.

That flexibility does not weaken runtime reproducibility or ownership:

- the source manifest records checkout location, commit, dirty-tree digest, dependency-lock digest, pack manifests, and capability definition digests;
- the generic pack host restarts or deliberately reloads before advertising changed capability digests;
- task admission pins the exact capability definition/source digest, and a later edit affects only later admissions;
- protocol/schema compatibility gates runtime connections, while whole-checkout commit/dirty state is diagnostic provenance rather than a global connection gate;
- runtime, Astrid, and workers remain separate processes/environments and may communicate only through generated clients and the worker protocol;
- public installers, wheel/signed-artifact gates, automatic update/rollback, and cross-machine distribution are deferred; and
- Git/source editing replaces the legacy dynamic pack installer, not the pack model itself.

The beta does not require or include:

- Reigh Worker or its Supabase-era control plane;
- Supabase-backed REIGH auth, credits, storage, or Edge Function code;
- local NVIDIA generation on unsupported hosts;
- Turso, hosted relay, remote collaboration, or RunPod;
- a generic third-party schema/capability plugin platform;
- multi-realm selection/switching, parallel named runtime daemons, and Linux support/certification;
- automatic CAS garbage collection or destructive storage reclamation;
- GPU bin-packing, partial-VRAM scheduling, priorities/fairness, model-affinity optimisation, thermal control, provider quota sharing, or per-project storage quotas;
- signed/notarized public installers, automatic update/rollback, polished uninstall/purge, multi-user support, or a supported migration matrix.

Optional provider-backed Astrid capabilities may use the internet when explicitly invoked and configured. Core workspace operations, local CPU/render work, backup, restore, and inspection must work with networking disabled except loopback. Beta support is intentionally limited to this user's current machine/environment; cross-platform release certification is post-beta.

### 3.2 Beta scope chosen for execution

The beta is complete only when all four are true:

1. **Legacy authority is gone.** Every legacy project-tree, sidecar, direct-database, old bridge, file event, projection, and in-process writer path is deleted from the supported source/process/runtime graph, with static and runtime proof.
2. **Astrid has broad capability parity.** Every currently relevant Astrid capability is ported to the neutral executor path or receives an explicit, truthful optional/unsupported/retired disposition. Nothing silently disappears; the beta required set is substantially broader than the small developer-preview floor.
3. **The REIGH handoff is concrete but deliberately narrow.** The generated TypeScript client and fake second-product conformance cover connection/scoped identity, projects, managed media ingestion and playback-critical byte semantics, the minimum renderable timeline/shot/reference shape, tasks/runs/events, cancellation/retry, rendering, and fake-worker settlement without Astrid types. Gallery, extension, and fuller REIGH composition/query contracts move to Stage 2 unless Astrid parity itself requires their neutral storage semantics.
4. **This machine's existing Astrid work is migrated once.** The migration is preceded by a verified immutable backup, produces reconciliation/hash/integrity evidence, activates atomically, and retains a rollback archive. General-purpose migration UX is deferred.

After the beta is working end to end, run the exhaustive crash/race/disk-full/corrupt-CAS/credential/security program as the first post-beta hardening phase.

### 3.3 Ground-truthed current baseline

The current Astrid implementation supplies useful extraction material but is not the product described here:

- the current checkout's `astrid` entry point prints the gateway/help surface; it is not a one-step product bootstrap;
- `astrid serve --no-open-editor` on a pristine projects root initializes a healthy WAL database and bridge, but creates neither a first-class realm nor a project/selection/timeline;
- `projects create` currently creates the database plus `project.json` and `plan.md`, so file-side state still survives beside the kernel;
- doctor already distinguishes pristine/uninitialized and initialized/healthy roots and checks schema, SQLite integrity, and foreign keys;
- the current bridge is a narrow Reigh integration rather than a complete Astrid product API, and `serve` still discovers/opens a Reigh editor path;
- the long-lived serve process owns the database exclusively, while ordinary CLI/SDK composition still expects direct application/database access instead of routing all concurrent clients through one daemon;
- the current repository-oriented Python wheel (`0.1.0`) is incidental; the beta target is an explicit editable-checkout composition, not a signed/notarized application or installer.
- the live schema is already composed from core plus timeline, shots, references, and runaway schema packs; its extraction disposition must be decided rather than silently flattened or imported as Astrid code;
- current media supports managed, external-local, and remote locators; the local-v1 cutover intentionally changes this to ingest-only managed CAS for runnable local media;
- additional in-tree surfaces—including pack management, threads, elements, model catalog/theme/audit/skills helpers, Remotion state, per-project CAS paths, secrets/session files, in-process executor routes, and Reigh/Supabase integration leftovers—are outside the eight-family census but still require explicit disposition.

T0 must turn these observations into committed, repeatable baseline fixtures. They are evidence of a strong kernel substrate, not evidence that the standalone Astrid product is already shippable.

## 4. Frozen architecture

The following may not be traded away to make the Astrid milestone faster:

1. The runtime is a sibling neutral repository and independently runnable service. Runtime source imports neither Astrid nor Reigh.
2. The runtime daemon is the sole SQLite, CAS, queue, migration, and coordinator writer.
3. Astrid and the generic pack host use the generated Python protocol client. They never open the database or call runtime repositories/object-store internals in process.
4. A workspace realm is one database plus one object namespace. Projects are rows inside it, not directories.
5. Structured state belongs in SQLite; immutable bytes belong in CAS; attempt staging is disposable.
6. Normal operation never scans, synchronizes, repairs from, falls back to, or dual-writes legacy project trees.
7. Path-dependent capabilities receive attempt-local materializations and return staged outputs. Paths never identify durable cross-process inputs.
8. Admitted work pins capability, protocol, timeline/media/settings versions, input digests, actor, and idempotency identity.
9. Claims and attempt mutations are epoch-, task-, attempt-, lease-, and version-fenced.
10. The offline migrator is the only normal source/process graph allowed to understand the old Astrid database and filesystem layout.
11. An Astrid-first source composition and a later Reigh-first/full-stack composition discover and reuse the same compatible runtime and realm; neither starts a private authority.
12. The first protocol is not limited to operations Astrid happens to expose, but Stage 1 freezes only proven shared semantics: scoped actors, projects/documents, managed media plus playback-critical byte operations, the minimum timeline/shot/reference composition, generations/variants required by Astrid parity, tasks/runs/events, capability/executor registration, rendering, and worker fences. Gallery-specific queries, extension management, and fuller REIGH composition enter as Stage 2 contract deltas when proven.
13. Local-v1 flattens current core + timeline + shots + references + runaway schema-pack migrations into one reviewed neutral migration stream without preserving a schema-pack host or inventing a bespoke `runaway` protocol operation. Existing facts survive as neutral records, versioned documents, relations, or migration evidence until a second client proves a dedicated semantic contract.
14. Local-v1 media is ingest-only for runnable local work. `external_local` sources are migrated into verified CAS or migration fails closed; no admitted task in the supported composition may depend on a persistent user path or reference-in-place mode.
15. Compatibility has three levels: protocol/schema compatibility gates a connection; capability/source digests pin admitted tasks; whole-checkout commit and dirty-tree state are recorded provenance, not a connection gate.
16. A worker receives no general workspace-mutation authority. It returns immutable typed outputs, a client-applied proposal, or only the predeclared settlement effect included in the admitted task and validated atomically by the runtime.
17. Stage 1 resource scheduling is intentionally minimal: one generic host advertises `max_concurrency` and named resource keys; capabilities declare requirements; reservations are tied to attempt leases; disk-heavy work preflights space; and queued tasks expose an exact waiting reason.
18. Stage 1 CAS is append-only. The runtime accounts for bytes and refuses work that cannot reserve enough space, but performs no automatic object deletion or garbage collection.

## 5. The Astrid launch contract

### 5.1 What “launch Astrid” means

The neutral `banodoco-local` Astrid-profile bootstrap owns the first-run state machine. The Astrid checkout launcher invokes it and presents its progress/errors; Astrid does not duplicate discovery, source activation, realm selection, credentials, locking, or compatibility logic. This same state machine is later reused by REIGH profiles.

The post-cutover public Astrid product surface is the five product families (`projects`, `timelines`, `media`, `tasks`, `runs`), the shots/references nested mounts, read-only `doctor`, and backup operations implemented as neutral-runtime client commands. Packs and skills remain first-class developer/agent source surfaces through SDK discovery, validation, authoring guidance, and lightweight harness sync/status tooling; they are not workspace CRUD families. `--help`, `--version`, and doctor remain side-effect-free. `astrid serve` is removed: no alias, editor open, private port, database composition, or transition release. The Astrid launcher invokes `banodoco-local up --profile astrid` using the configured editable source manifest and the one selected current-Mac realm. Ordinary product commands discover/connect to the selected runtime and, if it is stopped or unconfigured, fail with that exact next action. They never create or migrate authority themselves.

### 5.2 Clean-machine first launch

The launch transaction is:

1. Before creating anything, detect a legacy Astrid projects root/database/config without a neutral activation manifest. Activation manifests live at `~/Library/Application Support/Banodoco/runtime/activations/<realm-id>.json`; they contain the source archive hash, destination realm/database/object-manifest hashes, runtime/schema/protocol/importer versions, and validation report digest and are referenced from the catalog. Refuse to create a parallel empty realm and return the exact offline migrator command; launch never auto-migrates.
2. Read the neutral persistent realm catalog and the ephemeral live discovery advertisement:
   - catalog: `~/Library/Application Support/Banodoco/runtime/catalog.json`;
   - live discovery: `~/Library/Application Support/Banodoco/runtime/discovery.json`.
   The atomically replaced, owner-only catalog contains known realm IDs/display names/data-root references, activation-manifest references/digests, the neutral machine-default selected realm, and configured source-profile references. It is machine composition state—not creative authority—and is owned/mutated only by the neutral bootstrap/runtime. Live discovery is process advertisement only: endpoint, PID, runtime instance ID, active realm, coordinator epoch, protocol/schema/capability versions/digests, and credential-file references. It may disappear on reboot and contains neither raw secrets nor a database path.
3. If a runtime is registered, verify PID, instance lock, protocol/schema compatibility, and health before reuse. Checkout commit/dirty differences are reported but do not reject the connection; a capability digest mismatch rejects only admission to that capability. An incompatible runtime protocol/schema fails closed with the exact reconfigure/restart action; launch never starts a second owner.
4. If absent, resolve the configured independent runtime checkout/environment from the source manifest and start it on loopback. Missing or mismatched source/dependencies fail with an exact editable-setup action rather than downloading or installing a hidden private runtime.
5. Reuse the catalog's one valid selected realm, or create one realm with an opaque ID and caller-supplied display name when none exists. Multiple-realm selection/switching is explicitly unsupported in Stage 1 and fails with an exact follow-up-stage diagnostic rather than guessing.
6. The runtime alone acquires the realm owner lock, creates the workspace root, initializes/migrates SQLite, creates CAS/staging roots, advances the coordinator epoch, and verifies integrity.
7. Bootstrap or load a distinct 256-bit Astrid-scoped actor credential from `~/Library/Application Support/Banodoco/credentials/`. Files are owner-only and raw credentials never appear in discovery or logs. Stage 1 proves scope enforcement, permissions, and no-secret logging; rotation/revocation/theft matrices remain hardening. Legacy `.env`, `this.env`, bridge token, and `~/.astrid` credentials are migration inputs, not live precedence layers.
8. Persist the neutral machine-default realm in the catalog and the actor's selected realm in SQLite after open. No Astrid-owned or project-side preference may decide workspace authority.
9. Run the lightweight handshake/doctor and expose the workspace only after required checks pass.

Steps 1–9 are the **core bootstrap** implemented and accepted at T2. Executor activation is a separate post-bootstrap profile phase added by T4: start the one generic Astrid pack-executor host from the source manifest, register capability/source/resource declarations, run preflight, and report truthful availability. The core workspace becomes healthy without the host running; beta Astrid becomes ready only when its required T0 capability floor is satisfied.

All bootstrap steps are idempotent. Two concurrent compatible launches yield one runtime owner and one realm; the loser reconnects. An incompatible loser exits without mutation. Stage 1 proves ordinary process restart and one machine reboot; exhaustive interruption points and stale-support-state combinations remain Stage 3.

One daemon serves the one Stage 1 realm. After reboot, bootstrap resolves that realm from the persistent catalog, verifies the owner lock and integrity, opens it, and rewrites live discovery without scanning workspace directories or creating a parallel realm. Realm switching, parallel named daemons, and Linux runtime-directory behavior are deferred.

### 5.3 Workspace shape

The runtime creates:

```text
<realm-root>/
  workspace.sqlite3
  workspace.sqlite3-wal
  workspace.sqlite3-shm
  objects/sha256/<shards>/<digest>
  staging/<active-attempt-id>/
```

Runtime discovery, credentials, bounded logs, source checkouts/environments, models, caches, backups, and explicit exports live outside the realm root.

“Everything syncs toward the workspace” means **managed ingestion and transactional mutation**, not background folder mirroring:

- project/timeline/task/run/note/experiment/preference state is written through protocol commands to SQLite;
- imported or generated durable files are hashed, uploaded, verified, and related through CAS-backed media records;
- a user source path exists only for the duration of import;
- capability sandboxes are attempt-local and disposable;
- exports are explicit derived artifacts and never become a second live authority.

First launch creates a realm, not a fabricated creative project. The first `projects create` command creates the first project row and its runtime-owned empty working document.

## 7. Capability and execution contract

Astrid cannot be called broadly usable merely because CRUD works. Every current public capability/facade is classified in a checked manifest as one of:

- **required and checkout-provided:** present in the supported source profile, registered, ready, and proven end to end;
- **optional and configured:** discoverable with an explicit unavailable reason until its dependency/credential/model is installed;
- **unsupported for this platform:** hidden from normal selection or reported unavailable with the exact supported profile;
- **retired:** removed from discovery, docs, aliases, tests, and supported source manifests.

No capability may be advertised as available without a digest-matched executor registration and a passing preflight.

The capability cutover must cover:

1. SDK invocation admits a run/task through the runtime; there is no direct `run.py` or database shortcut.
2. The generic Astrid pack-executor host claims the immutable snapshot, reserves its declared resource keys, materializes authorized media/documents into its fenced attempt directory, runs the pack unit, and stages immutable typed outputs.
3. Task admission declares either artifact/result-only settlement, a client-applied proposal schema, or one narrowly typed settlement effect with allowed targets and expected versions. The worker receives no general workspace-mutation credential.
4. Runtime settlement verifies hashes, schemas, expected versions, the full attempt/resource fence, and the predeclared effect; it publishes objects, applies only that effect, writes output/media/provenance records, advances task/run state, and appends event/receipt atomically. Any undeclared effect fails without partial publication.
5. Orchestrators admit children only through the active parent-attempt protocol with allowlist, depth, fan-out, dependency, cancellation, and idempotency checks.
6. Cancellation, retry, lease expiry, worker death, runtime restart, late settlement, and resource-reservation release have deterministic outcomes.
7. Final capability outputs remain usable after the attempt directory and original imported paths are removed.
8. REIGH-named handoff/publish capabilities are classified as explicit optional integrations or retired for Stage 1; they cannot remain hidden legacy paths or be implemented inside Astrid.
9. GPT/LLM and hosted-provider execution is not an Astrid side channel: any paid call, reproducible analysis, artifact-producing operation, or durable mutation is admitted as a task and executed by a registered host with scoped credentials. Only ephemeral conversational reasoning may remain outside task admission.
10. Each worker advertises `max_concurrency` and named resource keys. Each capability declares its required keys and estimated scratch/output bytes. Reservations share the attempt lease and release on completion, failure, cancellation, or expiry; tasks expose exact blocked reasons such as `waiting_for_worker`, `waiting_for_gpu`, `insufficient_storage`, or `provider_rate_limited`.

The beta matrix must include the five product families, shots/references mounts, backup/doctor, one deterministic fake capability, local CPU/analysis work, managed rendering, GPT/provider-backed work, orchestrators, and the currently useful image/audio/video generation facades. Broad parity means every currently useful capability on this machine has a working neutral-worker route. A redundant model/backend implementation may be unavailable only when the same product capability remains available through the accepted profile or when a concrete platform/credential dependency makes it impossible; no capability family is cut merely to reduce the port. Full pack census coverage decides every entry explicitly; silence is not a disposition.

Parity proof is proportional to distinct behavior rather than raw manifest count:

1. every manifest validates, registers, and preflights truthfully;
2. every distinct executor implementation/adapter family passes a real end-to-end task;
3. every high-use, high-risk, or semantically unique capability passes its own real end-to-end task;
4. equivalent aliases, model variants, and provider modes may use schema, fixture, replay, or fake-provider tests when they share the proven adapter; and
5. no capability reports `ready` unless its actual credential/model/tool prerequisites are present.

The [ten provocative boundary tests](./00-overall-strategy.md#31-ten-provocative-boundary-tests) are Stage 1 acceptance rules, not explanatory prose. The census and process traces must demonstrate each one.

## 8. Astrid-First Beta Trunk

Each tranche has a hard exit gate, but overlap is the default. A lane waits for its named schema, operation, client, fixture, or runtime slice—not for an entire preceding tranche. No later tranche may paper over a failed earlier gate with a fallback.

### Parallel-first workstream topology

Stage 1 applies the overall strategy's work-packet contract using this standing topology:

| Lane | Exclusive ownership | Earliest safe start | Convergence point |
|---|---|---|---|

| Sustained productive shape | Provisional elapsed Stage 1 |
