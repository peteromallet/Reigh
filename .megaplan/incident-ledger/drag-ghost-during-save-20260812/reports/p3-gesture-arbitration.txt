## Verdicts (evidence pack: `docs/timeline-save-sync-incident-20260811.md` + artifacts)

**1. finally-drain during a drag — refuted.** `doSave`'s `finally` (useTimelinePersistence.ts:385-397) has **no** `isInteractionActive` gate and can run mid-drag — but it is drag-invisible. It only mutates persistence refs (`isSavingRef`, `pendingSaveRef`, `saveStatus`). The re-entrant POST's `onSuccess` *can* fire `commitData` mid-drag (signature gate at :317-328 holds because a drag applies no edits), but it writes `{...latest, configVersion}` — rows/tracks/meta are **same array references**, so `computeDropPosition` (drop-position.ts:92-118, reads `dataRef.current.rows/tracks`) sees identical rows. The resulting re-render cannot kill the drag: listeners are window-level (useClipDrag.ts:441-443), the floating ghost is raw DOM, and the effect's deps are stable refs `[dataRef, timelineWrapperRef, pixelsPerSecondRef]` (:459) — a save re-render never re-runs cleanup/`endSession`.

**2. deferredSaveRef / onInteractionEnd flush — refuted.** `deferredSaveRef` is written only by `scheduleSave` behind the gate (:443-449) and drained only by the flush listener (:507-516). The flush fires exclusively via `notifyInteractionEndIfIdle`, which only interaction writers call after flipping a flag false; the save layer never calls it, so a flush mid-drag is impossible. Drop-order is also safe: `commitDraggingSession` runs **before** `endSession` (:374-388), so the drop's `scheduleSave` is deferred while `drag` is still true and flushed cleanly after.

**3. isInteractionActive / gestureOwner toggling — refuted.** The save layer only *reads* `isInteractionActive`; writers are `useClipDrag` (drag=true enterDragging:253, false endSession:159) and resize. `setGestureOwner` has 14 call sites, all gesture/overlay writers — never persistence. `mobile-interaction-model.ts` has **no `claimPointer`** (pure policy module); pointer claims exist only in `TimelineExtensionOverlayHost` (extension path, owner `'overlay'`), disjoint from clip drag.

**4. commitData queued? — refuted.** `commitData` is fully optimistic and synchronous (`dataRef.current = nextData; setData` at useTimelineCommit.ts:262-263). The only queue is the network layer (`pendingSaveRef`, stale snapshot from :482). `computeDropPosition` therefore never reads a torn `dataRef`; the sole mid-drag writer (coupling 1) is row-identity-preserving. `managedObjectGuard` lives only in the command facade (useTimelineCommandsService.ts:365-376), not in the drag's `applyEdit` path.

**Confidence: high.** Negative searches: `claimPointer` (30 hits — overlay host/tests), `setGestureOwner` (14 — gesture writers), `setPointerCapture` (5 — none in clip drag), `managedObjectGuard` (command facade only), `computeDropPosition` (coordinator/drop-position only). No race found; deferral/drain bookkeeping cannot release the owner or desync the ghost.
