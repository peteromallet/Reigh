## Mechanism (from `useTimelinePersistence.ts`)

`SaveStatus = 'saved'|'saving'|'dirty'|'error'` (`:18`; no `idle`/`conflict`). Transport catch (`:332-363`): `setSaveStatus('error')` + `scheduleErrorRetry` — exponential backoff `500ms·2ⁿ` capped `8_000ms` (`:31-32,240`), unbounded attempts. Watchdog: `scheduleSave` arms once per edit (`armWatchdog`, `:417`, grace `5_000ms` `:38`); **not re-armed by retries** (`:243-256` calls `doSave` directly). Cleared only by `saveSuccess` → `clearWatchdog` (`:575`), reload (`:500`), or Retry save (`:466-477`).

## saveStatus + watchdog timeline (one cycle)

1. edit → `scheduleSave`: `dirty` (`:431`), watchdog armed (fires t+5s)
2. +500ms debounce → `doSave`: `saving` (`:277`)
3. transport failure → `error` (`:359`), backoff timer
4. retry fires → `saving` again; badge error clears at retry start
5. ack → `clearErrorRetry`, `saved` (`:304,327`), emit `saveSuccess` → banner (if tripped) clears

So the error badge shows **during backoff windows** (transient), while the banner trips at 5s if a slow in-flight save (or still-failing retries) hasn't acked — and both auto-clear when the save later succeeds. That matches "error before save eventually succeeds" without user action → fix category: **b** (watchdog false alarm), with **a** as the real-but-transient badge.
